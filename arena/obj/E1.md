# E1: does Hetzner Object Storage carry the keeper's protocol

E1 decides whether the generation authority can be the store itself. The keeper claims a generation by creating `g/<gen>` exclusively and trusts `List` to show it at once. The probe tests those assumptions first, then the read path, then a soak.

## Before you run (owner)

1. Create an Object Storage bucket in the Hetzner Cloud Console, in the same location as the Cloud box that runs the probe (fsn1, nbg1 or hel1). Leave versioning off: the keeper will use an unversioned bucket, and the docs list conditional PUT only for versioned ones.
2. Create S3 credentials in the Console and put them in the box's env. Never commit them or paste them into a report.
3. Build and copy the probe, with no network dependency on the box:
   `GOOS=linux GOARCH=amd64 CGO_ENABLED=0 go build -o a ./arena/a`

## Run

```
export AWS_ACCESS_KEY_ID=...  AWS_SECRET_ACCESS_KEY=...
./a probe -store 's3://BUCKET/e1?endpoint=hel1.your-objectstorage.com&region=hel1' -n 30 -soak 0 -out e1-cells.json
```

`region` is the location name (fsn1, nbg1, hel1). The backend uses path-style URLs, `https://<endpoint>/<bucket>/e1/<key>`, so bucket names with dots need no wildcard certificate. Run the cells first. Run the soak only if every cell passes:

```
./a probe -store '<same>' -n 30 -soak 24h -out e1-soak.json
```

The soak rotates four ops about every 200 ms (two 64 KiB range reads, one manifest put plus list, one 1 MiB range read): roughly 5 ops/s, 6 requests/s, well under the 750 req/s limit. Over 24 h that is about 127 GB read from the bucket and up to 108,000 small objects written, all deleted at the end. Check Hetzner's traffic pricing before the go. Ctrl-C or SIGTERM stops the soak early and still cleans up.

## Reading the result

Every cell prints `n`, `err` (transport, status or timeout errors), `miss` (the assumption was violated while the call succeeded), p50 and p99 in ms. With 30 samples p99 is the max, so K1 is judged on the soak when there is one. The JSON in `-out` carries the same numbers and the verdicts. The exit status is non-zero when any check fails.

Cell order is the protocol order, interleaved per sample:

| Check | Cells | Fails when |
|---|---|---|
| A1 conditional create refuses a second writer | `putx.create`, `putx.conflict` | the first create errors, or the second returns success |
| A2 create is visible to List on `g/` at once | `gen.create+list` | List after a returned PutExclusive lacks the key or any earlier gen |
| A3 exactly one winner under a race | `gen.race` | four concurrent PutExclusive on one key do not give exactly one success |
| A4 list-after-write is strong on `m/` | `manifest.put+list` | List after Put lacks the key or any earlier manifest |
| A5 presigned Range reads are exact | `get64k.range`, `get1m.range`, `get8m.range` | a status other than 206, or bytes differ from the uploaded blob |
| A6 Delete visible to List, missing key no error | `delete+list` | the key still lists, or deleting a missing key errors |

If A1 fails on the first sample the probe stops and prints `ABORTED` with the status the endpoint returned. Report that outcome as it is. Conditional create then moves out of the store and the generation authority becomes a control-plane service, which is an owner call.

## Kill thresholds (proposed, owner calls)

| Check | Kill when |
|---|---|
| K1 | 64 KiB range GET p99 over 500 ms |
| K2 | errors and timeouts over 1% of ops |
| K3 | any list-after-write miss (A2, A4, A6) |
| K4 | presigned PUT unusable: not applicable, the keeper uses no presigned PUT |

## Cleanup

The probe writes under `e1/probe/<unix>-<hex>/` and deletes everything it wrote on exit, printing `cleanup: N keys`. If the process was killed hard, list the bucket under `e1/probe/` in the Console and delete the prefix. Delete the bucket and the credentials when E1 is done.
